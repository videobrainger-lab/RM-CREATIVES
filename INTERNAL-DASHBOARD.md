# Internal performance dashboard

Production route: `https://rmcreatives.com/internal/`. The main public Astro site is unchanged. The dashboard is served by a Netlify Function; no private data is emitted into static files, the sitemap, or this repository.

## Access

`RM_DASHBOARD_PASSWORD` is a production-only secret in the Functions scope. Visitors enter the shared password and receive an HMAC-signed, Secure, HttpOnly, SameSite=Strict cookie for seven days. Changing the password invalidates existing sessions. Page and API responses use private/no-store and noindex. Direct function routes and the background refresh also authenticate. Never put passwords or API keys in this repository.

## Data

Google Ads and Meta advertising data are queried through Windsor. Initial daily data was loaded through the connected Windsor tool. This is a dated snapshot until the owner supplies a Windsor API key in the authenticated Connections dialog. The key is stored server-side in private Netlify Blobs and is never returned by an endpoint.

Once configured, a scheduled function starts the authenticated background refresh at 04:00 UTC (07:00 Moscow). Four queries load the preceding 90 complete days, including campaign spend, conversion events, current conversion definitions, and Meta website events. Queries run outside the browser; long-running pending reports are polled. A failed refresh preserves the last complete snapshot. Manual refresh is available in the dashboard. After 90 days, older data rolls out of the snapshot.

The `rm-kpi-production` site-wide store contains snapshot, settings, and sync status objects. The production-only password is withheld from preview deployments; never configure a preview with the production password. Reads and writes require the password/session. The authenticated `/internal/import` endpoint is for complete initial/recovery advertising snapshots, not client records or PII.

Campaign IDs and account mappings live exclusively in the private snapshot; `netlify/lib/kpi-model.mjs` contains only public project labels and calculation logic. Unknown MILO campaigns default to Shared/unallocated. Review that list when adding new delivery/services campaigns. EUR and USD are kept separate. Platform conversion counts and attributed revenue are not added into unique business totals.

Google Primary uses `conversions` under campaign goal settings. Secondary sums events explicitly classified as secondary in the currently returned action definitions. Historical changes to action definitions cannot be reconstructed from this snapshot. Unclassified nonzero events make derived event metrics unavailable. Purchase counts use the Purchase category; booking counts require the explicit booking_created event name, rather than treating every Book appointment category action as a real booking.

DENTA now supports a separately stored aggregate CRM snapshot from its exact Google Sheet. Pulse totals and rows include only Google Ads and Meta; unattributed and other sources remain excluded. Daily counts use enquiry receipt dates and current booking status (Pierakstījās), not advertising conversions. Duplicate inquiry IDs are removed before aggregation. Missing booking-event dates are disclosed; visit counts remain unavailable when visit status/date tracking is unfilled. Partial CRM periods display known counts and suppress CPA. Only daily counts and source metadata are uploaded; patient records and identifiers stay outside the app. The authenticated /internal/crm-import endpoint persists crm-denta separately from advertising refreshes. CRM imports are manual snapshots, not an active Google Sheets sync. EPILINE business outcomes remain unavailable; MILO delivery orders and services are imported separately from their CRM sheet. Neither of the connected BigQuery links returned datasets for the EPILINE project in this session. Kommo's current lead stage is not a historical booking/visit event feed. Do not fill business metrics using advertising clicks, current CRM stages, or inferred zeroes.

## Validation

Run `node --test tests/*.test.mjs` and `npm run build`. Security, CSRF, ranges, allocation, currencies, missing data and purchase/booking semantics have dedicated tests. The dashboard has a separate CSS and JS bundle and loads no marketing trackers.

## MILO SEO / GEO

The MILO view adds six KPI cards, a six-month history, AI diagnostics and commercial-query visibility. Default period for the MILO deep link is 28 complete days. Revenue uses GA4 `gross_purchase_revenue`, without cancellation or refund deductions; orders are recorded GA4 ecommerce purchases, not verified payments. Attribution is session-based Organic Search, with known AI-host referrals separated before aggregation. Nonbrand clicks exclude MILO / MĪLO / МИЛО from visible Search Console queries; hidden queries are not estimated, and query revenue is not fabricated.

The verified MILO GA4 property currency is USD. EUR is an explicit conversion using the ECB daily USD-per-EUR reference rate, falling back to the preceding business day within seven days. It is not the original EUR order value. Unknown currency/rates produce missing revenue, never a relabelled USD amount. Landing categories retain shared home/menu pages under Other instead of assigning them to a city. Commercial-query top-3/top-10 uses impression-weighted Search Console average positions for visible nonbrand commercial queries from Latvia. It is explicitly labelled as GSC average-position visibility, not fixed-query local rank tracking. AI recommendation share still needs a verified monitoring source. Google GenAI impressions have a separate GSC report, but the current Windsor connector does not expose it; a verified CSV export is needed. An absent report is not a measured zero.

Private source mapping uses production Functions environment variables `RM_MILO_GA4_PROPERTY` and `RM_MILO_GSC_SITE`. Existing Windsor credentials stay in private settings. The independently authenticated background function `internal-seo-background` refreshes GA4, ECB and Search Console; daily refresh is started alongside advertising at 04:00 UTC. Authenticated `/internal/seo-refresh` starts a manual refresh. The initial MILO view starts it once when the existing Windsor key is configured and no SEO snapshot exists. Production password/session protection, CSRF checks and preview isolation apply unchanged.

Private `seo-milo` stores only daily aggregated metrics (no query text, landing URLs, transaction IDs or customer records; commercial positions retain only SHA-256 query fingerprints and daily impression/position aggregates so period averages can be recomputed); `seo-sync-status` reports progress. Each source replaces its previous aggregate only after complete success; failures preserve earlier data and dates. Search Console is queried in consecutive 28-day chunks with a three-day delay. Current and comparison windows shift equally to its last available day, with the actual dates shown on the click card. The graph uses calendar months, with source coverage gaps kept as missing values. This feature does not alter the existing advertising snapshot, CRM aggregation or MILO checkout.


## MILO CRM overview and paid delivery (2026-10-29)

MILO now starts with all-source delivery order count and order value, including unknown and nonpaid sources. These are placed before paid delivery, followed by the existing services/shared campaigns and SEO/GEO. Services enquiries and GA4 purchases are not added to delivery orders. The landing-direction and page-language report was removed from the UI.

The `milo-delivery` v2 import declares exhaustive source coverage, EUR, and `completeThrough` separately from the last observed day. The source Google Sheet stays unchanged. `kpi-delivery-import.mjs` deduplicates by order ID before upload, rejects conflicting duplicates, then discards IDs. Existing v1 imports remain readable but cannot claim all-source or SendPulse coverage. Only daily channel counts and integer EUR cents are stored. Empty channel/day combinations within an exhaustive snapshot are real empty results; unavailable periods remain missing. Comparison deltas are suppressed unless both equal-length periods are complete. The source currently starts in October, so earlier September comparison history cannot be invented.

Paid delivery includes Google Ads, Meta Ads and SendPulse. Each channel calculates cost/order = channel expense / labelled CRM orders, and ROAS = labelled EUR order value / EUR expense. Overall expense and ratios require complete costs for all three channels; missing SendPulse cost must never silently become zero. Google/Meta channel ratios still work independently. Mixed currencies are not added. Zero orders suppress cost/order; zero spend suppresses ROAS. Current-day and partial CRM windows suppress all efficiency ratios.

Optional `sendpulseCosts` imports a complete inventory of MILO delivery campaign expenses for its declared coverage, with daily `spendMicros`, EUR and the original SendPulse report URL. Preserve sub-cent expense precision. Balance top-ups are not campaign expenses. A single campaign report cannot certify a whole month's expense. The connected SendPulse campaign list does provide SMS and email campaign charges, which were read without sending anything. Known campaign charges are imported with `complete:false` because prepaid email consumption has no allocated cost in the available API response. They display as the known part, while total expense and overall efficiency remain unavailable. Set `complete:true` only after that cost is resolved. SendPulse attribution requires an explicit verified SendPulse source, including a captured order-source line when the sheet category is Other; a generic email UTM is retained outside that paid channel. Conflicting paid-source evidence is rejected.

### Commercial-query visibility

`kpi-commercial-search.mjs` documents a versioned, conservative LV/RU intent dictionary, excludes MILO/MĪLO/Мило/Milu/Mila brand variants and informational recipe/definition/ideas queries, and requires Latvia plus positive impressions. Accented and unaccented queries remain separate GSC queries. Each query's period position is sum(position × impressions) / sum(impressions), then the query is counted once at <=3 and <=10. The card shows absolute top-3/top-10 query counts alongside their percentages. Percentages use the count of visible classified queries as denominator, not the number of impressions or daily positions. The population varies with the period; hidden queries are excluded. This is Latvia-level GSC visibility, not a Riga/Jurmala SERP tracker. GSC dates use Pacific Time; CRM uses Europe/Riga.

The SEO refresh independently updates the previous 90 settled days of query/date/country impressions and positions. It filters Latvia locally, commits only after the entire pull succeeds and keeps previous commercial data on failure. Existing GA4, ECB and nonbrand-click refreshes retain their independent failure behavior. The manual initial commercial snapshot covers two comparable 28-day windows; it contains no query text.

### AI answers: connection boundary

GA4 AI referral visits and purchases already work, but do not measure recommendations. To connect the recommendation card, agree a fixed LV/RU commercial question set, Riga/Jurmala context, models/providers and cadence, then use a verified source that retains dated answers/evidence links and a clear recommendation denominator. A manual audited answer log is possible before choosing a paid tracker. No subscription, new key or new access was created. Google's separate GenAI report measures link impressions in AI Overviews/AI Mode, not cross-provider recommendation share: https://support.google.com/webmasters/answer/16984139 .
